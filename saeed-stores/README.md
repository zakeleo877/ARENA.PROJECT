# محلات السعيد — تطبيق الزبائن وتطبيق الإدارة

> **الحالة: المرحلة الثانية، أساس الوحدة المشتركة.** ليس هذا إصدارًا جاهزًا للتوزيع؛ شاشتا التطبيقين ما زالتا مؤقتتين. التصفح والسلة وطابور الإرسال وتسجيل دخول المدير والواجهات الإدارية تُنفَّذ في المراحل التالية.

## المشروع

- تطبيق الزبائن: `com.zakeleo877.saeedstore`.
- تطبيق الإدارة: `com.zakeleo877.saeedadmin`.
- وحدات Gradle: `core` مشتركة، و`customer`، و`admin` مستقلان.
- العربية وRTL وAndroid 7.0+؛ قاعدة بيانات Supabase مشتركة. يبدأ جدول المنتجات فارغًا.
- يحتفظ `core` بخط Tajawal بثلاثة أوزان وترخيصه في `docs/licenses/Tajawal-OFL.txt`، مع ثيم Neon Void ومكوّنات Compose قابلة لإعادة الاستخدام.

## بنية المستودع

```text
core/                    الثيم والنماذج وKtor وRoom واختباراتها
core/schemas/            مخطط قاعدة Room المصدَّر للإصدارات اللاحقة
customer/                تطبيق الزبائن — شاشة مؤقتة
admin/                   تطبيق الإدارة — شاشة مؤقتة
supabase/schema.sql      جداول وسياسات ودوال القاعدة
supabase/tests/          فحص SQL محلي بمحاكاة محدودة لخدمات Supabase
.github/workflows/       فحص الوحدة المشتركة وSQL؛ لا يبني APK موقّعة بعد
```

## الأدوات والإصدارات

تمت مراجعة الإصدارات المستقرة في 04/11/2026 من فهارس Google Maven وMaven Central وGradle. القيم مثبتة في `gradle/libs.versions.toml` وGradle Wrapper. يتطلب المشروع JDK 17 وAndroid SDK `platforms;android-37.2`، مع `minSdk` 24 و`targetSdk` 37. نسخة Gradle Wrapper وتحميلها مثبتان ببصمة SHA-256.

تستخدم القاعدة المحلية Room 3.0.3 والحزمة `androidx.room3` مع `AndroidSQLiteDriver`، حتى لا تضاف مكتبة SQLite أصلية منفصلة. الحد الأدنى المعلن لـRoom هو API 23؛ اختبارات Robolectric هنا تعمل على API 24 و28، وليست بديلًا عن الاختبار على جهاز.

## الوحدة المشتركة وحدودها

- تصفح البيانات في المراحل التالية سيعتمد على `CatalogRepository`: تحديثات مكتملة فقط تستبدل ذاكرة Room، والخطأ يترك النسخة السابقة مع وقت آخر تحديث. لا يوجد تحديث آلي أو شاشة فعلية بعد.
- جدول `pending_orders` يهيئ تخزين نسخة الطلب و`client_id`، لكن **WorkManager والإرسال وإعادة المحاولة غير منفّذة بعد**. البيانات المحلية داخل مساحة التطبيق وغير مشفرة على مستوى التطبيق؛ النسخ الاحتياطي للتطبيقين معطّل. لا تخزّن بيانات حقيقية قبل إكمال مراجعة الأمان.
- `CatalogApi` يقرأ المنتجات والإعدادات العامة، ولديه طلب `place_order` لا يتضمن سعرًا أو إجماليًا من العميل. `client_id` ثابت لكل طلب لإتاحة إعادة المحاولة دون تكرار؛ التسعير الفعلي دائمًا على الخادم، وقد يتغير السعر قبل الإرسال.
- المنتجات غير المتاحة قابلة للقراءة العامة كي تعرضها واجهة الزبون معطّلة، لكن دالة الطلب ترفضها. لا تُدرج في الجدول معلومات منتجات يُراد إخفاؤها عن الجمهور.
- إعدادات Hilt وطبقة الاتصال جاهزة للربط، لكن الشاشتين المؤقتتين لا تنشئان المستودع أو تتصلان بـSupabase بعد.

## قرار الاتصال والأمان

بموافقة المالك، تستخدم الوحدة المشتركة وعمليات الزبائن المجهولة Ktor مع PostgREST مباشرة، بدل `postgrest-kt` التي تسحب `auth-kt`. ستستخدم الإدارة `supabase-kt` في مرحلتها. يُرسل مفتاح `sb_publishable_…` العام في ترويسة `apikey`، ويُضاف `Bearer` فقط عند استخدام مفتاح `anon` القديم بصيغة JWT. يرفض الكود مفاتيح `sb_secret_` وJWT ذي دور مرتفع؛ لا يثبت فحص العميل صلاحيات المفتاح أو سياسات المشروع.

لم يظهر Supabase Auth أو PostgREST Kotlin في تقرير `customer:debugRuntimeClasspath` الحالي، دون تبعيات فاشلة. هذا **ليس فحص APK نهائيًا**؛ يجب مراجعة نسخة الإصدار بعد اكتمال التطبيق.

## إعداد Supabase — لا تنفذ على بيانات حقيقية قبل النسخ الاحتياطي

1. يفضَّل إنشاء مشروع Supabase جديد ومخصص للمتجر، وآخر منفصل للاختبارات الأمنية.
2. قبل تهيئة الإدارة، عطّل **Allow new users to sign up** و**Anonymous sign-ins** من لوحة Authentication. تأكد أيضًا من عدم وجود أي حساب غير موثوق مسبقًا: أي مستخدم مسجّل الدخول قد يصبح أول مدير ما دام جدول المديرين فارغًا.
3. جرّب `supabase/schema.sql` أولًا في مشروع تجريبي. في مشروع الإنتاج الجديد فقط، نفّذه من SQL Editor بعد المراجعة. السكربت يستبدل **جميع سياسات RLS الموجودة على الجداول الأربعة التي يديرها** ويحدّث إعدادات حاوية صور المنتجات؛ لذلك لا تشغّله على مشروع قائم دون نسخة احتياطية ومراجعة. راجع أيضًا عدم وجود سياسات تخزين عامة سابقة تسمح بالكتابة في حاوية الصور.
4. أنشئ حساب المدير من **Authentication → Users → Add user**. عندما يُنفَّذ تسجيل الدخول في المرحلة اللاحقة، يستدعي تطبيق الإدارة دالة المطالبة الأولى مرة واحدة. لا تترك جدول المديرين فارغًا مع حسابات أخرى غير موثوقة.
5. يبدأ `products` فارغًا. لا تُستخدم بيانات عملاء حقيقية في الاختبارات.

### الإعداد المحلي والبناء

انسخ `local.properties.example` إلى `local.properties` وأضف رابط المشروع والمفتاح العام منخفض الصلاحيات فقط. قيم التطبيق المضمّنة في APK قابلة للاستخراج؛ الحماية الحقيقية هي RLS، فلا تضع مفتاحًا ذا صلاحيات مرتفعة داخل أي تطبيق. التوصيل الفعلي لإعدادات التطبيق بالوحدة المشتركة سيكون في مراحل الواجهات.

للتوقيع، انسخ `keystore.properties.example` إلى `keystore.properties`، وأنشئ مخزن توقيع خاصًا بك واحتفظ بنسخة آمنة خارجه. لا ترفع المخزن أو كلمات مروره أو الإعدادات المحلية إلى Git. ستضاف إجراءات البناء الموقّع في مرحلة التسليم، باستخدام GitHub Secrets.

بعد اكتمال المراحل وتوفر الأدوات والتوقيع، أوامر البناء المستهدفة هي:

```bash
./gradlew test lint
./gradlew :customer:assembleRelease :admin:assembleRelease
```

هذه الأوامر الشاملة **لم تُجتز بعد**. لا تُرفع APK إلى Git؛ ستكون لاحقًا مخرجات بناء عند نجاح إصدار موقّع.

## الفحوص المنفّذة

- نجح `:core:testDebugUnitTest`: 16 حالة، منها أربع حالات Room عبر Robolectric على API 24 و28، واختبارات Ktor MockEngine والتباين والتنسيق.
- نجح `:core:lintDebug` بلا مشكلات، ونجحت ترجمة Kotlin للشاشتين المؤقتتين. لم يُبْنَ APK أو تُجرَّب واجهة على جهاز.
- نجح `cd supabase/tests && npm ci && npm test`: 30 فحص SQL، بما فيها رفض طلب منتج غير متاح. Auth وREST وStorage هنا محاكاة محدودة وليست Supabase حقيقيًا.
- أُضيف سير GitHub Actions لهذه الفحوص، لكنه لا يُعد ناجحًا قبل تشغيله ومراجعة نتائجه. التفاصيل والحدود في `docs/phase-2-validation.md`.

## المراحل المتبقية

1. تطبيق الزبائن: ربط الإعدادات وHilt، والتصفح والسلة وطابور الطلبات دون إنترنت.
2. تطبيق الإدارة: الدخول والمنتجات والطلبات والفواتير.
3. اختبارات Supabase التجريبية، سير APK الموقّع، وفحص الإصدار على جهاز/محاكي.

يجب مراجعة كل مرحلة قبل الانتقال للمرحلة التالية.
