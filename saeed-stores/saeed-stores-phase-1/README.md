# محلات السعيد — تطبيق الزبائن وتطبيق الإدارة

> **الحالة الحالية: المرحلة الأولى فقط.** هذا مستودع قيد الإنشاء، وليس نسخة تشغيلية أو إصدارًا جاهزًا للتوزيع. شاشتا التطبيقين الموجودتان الآن مؤقتتان، ولم تُنفَّذ ميزات المتجر بعد.

## المشروع

- تطبيق الزبائن: `com.zakeleo877.saeedstore`.
- تطبيق الإدارة: `com.zakeleo877.saeedadmin`.
- ثلاثة أقسام Gradle: `core` مشتركة، و`customer`، و`admin` مستقلان.
- العربية وRTL وAndroid 7.0+؛ قاعدة بيانات Supabase مشتركة.
- إعدادات المتجر الأولية مطابقة للبرومبت الذي قدّمه المالك. يبدأ جدول المنتجات فارغًا.

## بنية المستودع

```text
core/                    وحدة مشتركة — الهيكل فقط حاليًا
customer/                مشروع تطبيق الزبائن — شاشة مؤقتة
admin/                   مشروع تطبيق الإدارة — شاشة مؤقتة
supabase/schema.sql      جداول وسياسات ودوال القاعدة
supabase/tests/          اختبارات PostgreSQL محلية ببدائل لاختبار المخطط
scripts/                 اختبارات Supabase الحقيقية ستضاف في مرحلة الفحص
```

## الأدوات المخطط لها

تمت مراجعة الإصدارات المستقرة في 04/11/2026 من فهارس Google Maven وMaven Central وGradle. القيم مثبتة في `gradle/libs.versions.toml` وGradle Wrapper. يتطلب المشروع حاليًا JDK 17 وAndroid SDK `platforms;android-37.2`، مع `minSdk` 24 و`targetSdk` 37. نسخة Gradle Wrapper وتحميلها مثبتان ببصمة SHA-256.

فحص إعداد Gradle وقراءة تبعيات الهيكل نجحا؛ **لم يتم بناء APK أو اختبار الواجهة على جهاز**. تفاصيل النتائج في `docs/phase-1-validation.md`.

## إعداد Supabase — لا تنفذ على بيانات حقيقية قبل النسخ الاحتياطي

1. يفضَّل إنشاء مشروع Supabase جديد ومخصص للمتجر، وآخر منفصل للاختبارات الأمنية.
2. قبل تهيئة الإدارة، عطّل **Allow new users to sign up** و**Anonymous sign-ins** من لوحة Authentication. تأكد أيضًا من عدم وجود أي حساب غير موثوق مسبقًا في المشروع: أي مستخدم مسجّل الدخول قد يصبح أول مدير ما دام جدول المديرين فارغًا.
3. جرّب `supabase/schema.sql` أولًا في مشروع تجريبي. في مشروع الإنتاج الجديد فقط، نفّذه من SQL Editor بعد المراجعة. السكربت يستبدل **جميع سياسات RLS الموجودة على الجداول الأربعة التي يديرها** ويحدّث إعدادات حاوية صور المنتجات؛ لذلك لا تشغّله على مشروع قائم دون نسخة احتياطية ومراجعة. راجع أيضًا عدم وجود سياسات تخزين عامة سابقة تسمح بالكتابة في حاوية الصور.
4. أنشئ حساب المدير من **Authentication → Users → Add user**. عندما يُنفَّذ تسجيل الدخول في المرحلة اللاحقة، يستدعي تطبيق الإدارة دالة المطالبة الأولى مرة واحدة. لا تترك جدول المديرين فارغًا مع حسابات أخرى غير موثوقة.
5. يبدأ `products` فارغًا. لا تُستخدم بيانات عملاء حقيقية في الاختبارات.

### الإعداد المحلي والبناء

انسخ `local.properties.example` إلى `local.properties` وأضف رابط المشروع والمفتاح العام منخفض الصلاحيات فقط. قيم التطبيق المضمّنة في APK قابلة للاستخراج؛ الحماية الحقيقية هي سياسات قاعدة البيانات، فلا تضع مفتاحًا ذا صلاحيات مرتفعة داخل أي تطبيق.

للتوقيع، انسخ `keystore.properties.example` إلى `keystore.properties`، وأنشئ مخزن توقيع خاصًا بك واحتفظ بنسخة آمنة خارجه. لا ترفع المخزن أو كلمات مروره أو الإعدادات المحلية إلى Git. يُتوقع استكمال سير البناء عبر GitHub Actions في مرحلة الاختبارات، باستخدام GitHub Secrets للبيانات اللازمة.

بعد اكتمال المراحل وتوفر الأدوات والتوقيع، أوامر البناء المستهدفة هي:

```bash
./gradlew test lint
./gradlew :customer:assembleRelease :admin:assembleRelease
```

هذه الأوامر **لم تُجتز بعد**، ولا ينبغي اعتبار الهيكل الحالي إصدارًا جاهزًا. لا تُرفع ملفات APK إلى Git؛ ستُنشر لاحقًا كمخرجات بناء عندما ينجح إصدار موقّع.

## فحص المخطط المحلي

```bash
cd supabase/tests
npm ci
npm test
```

تستخدم هذه الاختبارات PostgreSQL محليًا مع محاكاة محدودة لأجزاء Auth وStorage وRealtime. هي تساعد في كشف أخطاء SQL وRLS، لكنها **ليست** اختبارات واجهة Supabase أو اختبارات الأمان الفعلية المطلوبة على مشروع تجريبي. لا تتصل بإنتاجك، ولا تستخدم أسرارًا أو بيانات عملاء.

## قرار تقني مطلوب قبل تنفيذ طبقة الاتصال

البرومبت يشترط استخدام `postgrest-kt` وفي الوقت نفسه خلو تطبيق الزبائن من مكتبة المصادقة. في إصدار `3.9.0` الذي تم فحصه، تسحب `postgrest-kt-android` مكتبة `auth-kt-android` ضمن تبعياتها المعلنة: [بيانات الحزمة في Maven Central](https://central.sonatype.com/artifact/io.github.jan-tennert.supabase/postgrest-kt-android).

لا يحتوي هيكل تطبيق الزبائن الحالي على هذه المكتبات، ولم يتم الاختيار بصمت. البديل المقترح هو استخدام Ktor لطلبات PostgREST المجهولة في تطبيق الزبائن، مع الاحتفاظ بـ `supabase-kt` في الإدارة، بعد موافقة المالك وفحص الطلبات والمخرجات الفعلية. يرسل المفتاح العام الجديد في ترويسة `apikey` بدل اعتباره رمز JWT. استبعاد الاعتماد اعتباطيًا دون اختبار قد يكسر المكتبة؛ كما أن تقرير التبعيات ليس بديلًا عن فحص APK النهائي.

## المراحل المتبقية

1. الوحدة المشتركة: الثيم، النماذج، التخزين المحلي، وطبقة الاتصال بعد حسم التعارض.
2. تطبيق الزبائن: التصفح والسلة وطابور الطلبات.
3. تطبيق الإدارة: الدخول والمنتجات والطلبات والفواتير.
4. اختبارات Supabase التجريبية، GitHub Actions، وفحص APK الموقّع على جهاز/محاكي.

يجب مراجعة كل مرحلة قبل الانتقال للمرحلة التالية.
